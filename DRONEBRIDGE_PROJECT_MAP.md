# Карта проектов, веток и вариантов DroneBridge

Проверено **19 октября 2026** по GitHub API репозитория [DroneBridge/ESP32](https://github.com/DroneBridge/ESP32). Его `master` на момент проверки — `ed1b9ef8959dbbe9b8f7ed261e928604206cf3e0`, последний стабильный релиз [v2.4.1](https://github.com/DroneBridge/ESP32/releases/tag/v2.4.1). Описания ниже относятся к **upstream**, не к названиям веток нашего форка. Ветку в текущем репозитории менять не требуется.

## Четыре уровня, которые легко спутать

1. **Репозитории / продукты:** [DroneBridge/ESP32](https://github.com/DroneBridge/ESP32) — открытая прошивка ESP32; [DroneBridge/DroneBridge](https://github.com/DroneBridge/DroneBridge) — отдельная историческая система для Raspberry Pi/обычных Wi-Fi адаптеров (WifiBroadcast); [DroneBridge/Desktop](https://github.com/DroneBridge/Desktop) — Linux/x86-образ наземной станции; [DroneBridge/Docs](https://github.com/DroneBridge/Docs) — документация. [DLSE](https://dronebridge.gitbook.io/docs/dronebridge-for-esp32-drone-light-show-edition/overview-drone-light-show-edition) — **отдельный коммерческий продукт** на ESP32 со Skybrush/Wi-Fi-инфраструктурой/OTA. Его прошивки **нет как открытой ветки** `DroneBridge/ESP32`; открыт клиентский [DLSECommercialSupportSuite](https://github.com/DroneBridge/DLSECommercialSupportSuite) для настройки, лицензирования и обновления по Wi-Fi.
2. **Git-ветки** `DroneBridge/ESP32`: в основном снимки этапов разработки *одной и той же* открытой прошивки, плюс ветка сайта, эксперимент диагностики и автоматические обновления зависимостей. Не отдельные поддерживаемые продукты.
3. **Релизы** (`v2.0`, `v2.3.0`, `v2.4.1`) — стабильные точки поставки и ZIP со множеством бинарных **flavour** для разных чипов/разводок/интерфейсов. Тег релиза — не дополнительная ветка.
4. **Runtime-режимы** одной прошивки: Wi-Fi AP, STA-клиент, AP-LR, ESP-NOW AIR, ESP-NOW GND, BLE. `UART/JTAG ↔ радио`; это настройки режима, **не отдельные проекты/ветки**. В текущем ESP-NOW-режиме STA-интерфейс используется для радиоканала и не подключается к роутеру.

Несмотря на название нашего форка `DroneBridge-for-ESP32-Arduino-mode`, проверенный upstream `DroneBridge/ESP32` — **проект ESP-IDF**, с `idf.py`, `CMakeLists.txt` и `app_main()`, а не Arduino-скетч с `setup()/loop()`.

## Что *на самом деле* выбирать: продукт → прошивка → flavour → режим

| Потребность | Подходящая линия | Где работать | Ограничение |
|---|---|---|---|
| Готовый UART↔Wi-Fi шлюз на существующей LAN, GCS по UDP/TCP | ESP32 **master / stable v2.4.1**, режим **STA** | Собственная Wi-Fi AP, UART FC/датчиков, GCS; IP/REST | Много узлов нагружает AP; MQTT/датчики добавлять отдельно |
| Дальнобойный канал без AP; общие команды для группы | ESP32 **master / stable v2.4.1**, ESP-NOW **AIR+GND** | Один радиоканал + групповой ключ; GND через UART к внешнему шлюзу | Нет IP у текущего ESP-NOW GND, нет адресных ACK/ретрансляции/OTA; добавить в Hybrid Core |
| Wi-Fi LR с инфраструктурой ESP32 | ESP32 master, **AP-LR** (+ совместимые клиенты STA) | Другие ESP32, а не обычные телефоны; UART + сеть | Ниже пропускная способность; ограничения совместимости и конфигурации |
| Телеметрия к телефону/GCS без второго ESP32 | ESP32 master, **AP** или STA | TCP 5760, UDP 14550, REST | Меньше дальность, чем LR; обычные ограничения AP |
| BLE-канал к совместимому клиенту | ESP32 master, **BLE** | BLE-мост; веб-интерфейс может поддерживаться AP для настройки | BLE не замена масштабируемой Wi-Fi/ESP-NOW сети |
| Коммерческое шоу, Skybrush, удалённое питание, штатное OTA | **DLSE**, не ветка открытого master | Устройства подключаются по IP к шоу AP; UART MAVLink; Support Suite | Отдельная прошивка/лицензия; не бесплатное готовое ядро домашней автоматики |

**Flavour в ZIP v2.4.1 — это сборочные настройки, а не ветки:** [`create_release_zip.sh`](https://github.com/DroneBridge/ESP32/blob/master/create_release_zip.sh) делает бинарники для ESP32/S2/S3/C3/C6, для official C3/C6 или generic и с `USBSerial`/`noUARTConsole` в нужных случаях. [`main/Kconfig.projbuild`](https://github.com/DroneBridge/ESP32/blob/master/main/Kconfig.projbuild) показывает разницу: official — заранее выбранные GPIO (на C6 также RF-switch), USBSerial — **данные GND через USB Serial/JTAG вместо UART**, noUARTConsole — настройка консоли отладки, а не иной радиопротокол. Одна и та же сборка выбирает runtime-роль AIR/GND в веб-конфигурации. Наличие RF-switch/двух антенн **не означает два независимых Wi-Fi-тракта**.

**Итог для Hybrid Core домашней автоматики:** опираться на `master` v2.4.1 с отдельно разрабатываемыми `sensor_task`, `node_id`/`req_id`/ACK, шлюзом UART↔MQTT на GND. `espnow_air2airdiag` полезна только как пример *методики измерений* очередей/потерь, а не как новый базовый radio stack. Если один ESP32 должен одновременно держать MQTT через Wi-Fi STA и ESP-NOW, потребуется новая архитектура совместного режима на одном канале; **ни одна из перечисленных веток не предоставляет её из коробки**. OTA есть у DLSE, но не в открытой ESP32-прошивке; локальный `AGENTS.md` не разрешает добавлять его в этот репозиторий.
